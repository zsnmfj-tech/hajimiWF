## 实施中根据证据做的调整

1. 单一 jsQR 校验不足：Tom + 特殊字符 SSID 在 0.60 档可被 jsQR 解码，但 ZXing 拒绝识别（独立码图也失败，已排除卡片文字排版原因）。将原计划仅开发期的 ZXing 提升为运行时第二解码器；两者都成功才采用该档。
2. 专项审查通过延迟默认图请求复现图片竞态，已加入统一图片加载状态、提交新图时失效旧结果、生成入口门禁与回归测试。
3. 默认素材实际为生成的 PNG，保留原图，不使用计划中的 WebP 文件名。
4. 双解码测试还发现 ZXing 对一张无艺术修改的标准码出现方向相关定位误判：正向失败、旋转 180° 后成功，纯码解析也成功。运行时保留原图不变，仅在 ZXing 正向失败时对同一像素旋转 180° 重试；jsQR 仍须从原方向通过，码图、缩小图和最终 PNG 都不跳过校验。
5. 用户反馈初版可以识别并联网，但上传猫咪的轮廓不清楚。旧版 0.60 边长的纯黑白核心覆盖了数据格约 36% 面积，掩盖毛色与眼睛细节。新版首档改为 0.46 核心，只将中心亮度约束到深色不高于 55、浅色不低于 200（0–255），保留原图颜色与纹理；功能区域继续纯黑白。后续保守档为 0.60、0.90、标准码，所有档仍需双解码通过。
6. 上传后自动展开裁剪控件，提示放大猫脸、保留双耳。当前未加入自动抠图：背景分离不能单独解决二维码覆盖细节的问题，先验证本次直接减少覆盖的效果；也不对所有用户照片承诺辨识度。

## 自动化证据

细节增强版最终运行：`npm run typecheck`、`npm test`、`npm run build`、`npm run test:e2e` 均通过。17 个单元测试、12 个浏览器测试通过（Chromium 与 WebKit 各 6 个，耗时约 2.6 分钟）。每种浏览器完成六图 × 十载荷交叉解码；Chromium 有 57/60 组采用细节保留首档，WebKit 为 56/60，其余使用更保守的融合档，没有清晰版回退；清晰版另有显式回归测试。

新增图像回归检查黑猫、白猫、复杂背景三张图：数据区域与原照片的像素差异低于旧渲染的 65%，功能区域逐像素保持纯黑白，并且 315px 图可被双解码器识别。该指标防止重新覆盖细节，不能代替用户对自家猫的视觉验收。默认图/上传、特殊字符、下载、隐私请求、375px 无横向溢出、旧结果失效、图片加载竞态、旋转/压缩/非整数缩放继续通过。

生产构建 JS 为约 642 KB（gzip 约 186 KB），Vite 给出单包超过 500 KB 的体积提示；来自新增双解码器，非构建失败。当前优先保留本地双解码能力。运行时只请求本站静态资源，无第三方 CDN。

专项审查：安全复核未发现具体安全问题；架构复核发现的图片切换竞态已修复并复核闭合。提交前 `git diff --cached --check` 通过；构建目录只有站点 HTML、JS、CSS、默认图和第三方许可，不包含测试图片或输入数据。

桌面 1440px 与手机 375px 截图已实际查看；截图、虚构网络迎宾卡位于忽略目录 `output/`。没有真实网络信息进入源码或测试输出。
