## 2. 技术选择

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 页面 | 原生语义 HTML + TypeScript | 单页表单和 Canvas 足够，不引入路由、SSR 或组件框架 |
| 构建 | Vite，输出 `dist/` | 本地预览、依赖打包、静态部署；`base` 明确为 `/hajimiWF/` |
| 样式 | 单一原生 CSS，设计变量集中于 `src/styles.css` | 本项目规模小，不叠加 Tailwind/CSS-in-JS；这是对通用设计技能框架偏好的简化选择 |
| 二维码编码 | `qrcode` 1.5.4 | 现成标准编码器，自动版本与 H 纠错；锁版本，避免自写 QR 算法 |
| 绘制 | Canvas 2D | 方形裁剪、图片处理、模块保护、PNG 使用同一像素路径 |
| 运行时校验 | `jsqr` 1.4.0 | 从输出像素独立解码，比较原始载荷 |
| 自动测试 | Vitest 5.0.5 + Playwright 1.64.1；开发测试使用 `@zxing/browser` 0.2.1 | 字段测试、真实浏览器渲染、另一解码器交叉核对 |
| 托管 | GitHub Pages + GitHub Actions | 发布静态产物；应用没有服务端请求 |

2026-10-23 查询的 Vite 版本为 8.3.5，要求 Node `^20.19.0 || >=22.12.0`，本机满足；TypeScript 元数据版本为 7.0.2，Vitest 5.0.5 与 Playwright 1.64.1 的 Node 要求也满足。首轮按这些版本安装并固定 lockfile，实际组合仍须通过 P0 构建与测试；不在 CI 使用漂移的 `latest`。

最小替代方案是“标准二维码 + 中央猫头像”，可减少艺术渲染与验证工作；用户已于 2026-10-23 确认整图融合，不以该替代方案偷换验收目标。最小技术验证版只做输入、默认猫、融合与解码，不先搭完整 UI。

## 3. 数据流与接口边界

```text
Wi-Fi 表单 --> 校验/转义 --> QR 矩阵 ---------+
                                           |
默认 Tom / 本地上传 --> 方向/裁剪 --> Canvas 合成
                                           |
                                  jsQR 像素反解
                                   |       |
                                 通过      失败
                                   |       +--> 下一清晰档（最多三档）
                                   |                    |
                                   |                 标准码回退
                                   v                    |
                            预览与 PNG 导出 <------------+
```

不存在服务端 API 或数据库 schema。内部数据仅在内存流转：

| 数据 | 字段与约束 |
| --- | --- |
| WifiInput | `ssid`、`password`、`security`（wpa / open）、`hidden`；禁止自动去空格 |
| CatImage | 图片对象、宽高、来源 default/upload、归一化裁剪位置与缩放 |
| QrMatrix | 模块数量、黑白位阵、功能保留位阵；两个位阵尺寸必须一致 |
| RenderRequest | 单调递增编号、完整 Wi-Fi 载荷、裁剪后猫图、识别档位 |
| RenderResult | 请求编号、PNG Blob、矩阵版本、最终档位、校验状态；不打印载荷或密码 |

模块责任：

- `wifi.ts`：校验、UTF-8 字节计数、逐字符转义、载荷组装。
- `image.ts`：文件验证、解码、方向与透明处理、裁剪；失败保留旧图。
- `qr.ts`：调用编码器并转成项目内部矩阵。`qrcode` 的保留位信息属于源码层接口，不视为稳定公共 API；由单一适配器读取并锁定 1.5.4，测试检查功能区完整性，升级必须复验。依据为 [BitMatrix 源码](https://raw.githubusercontent.com/soldair/node-qrcode/master/lib/core/bit-matrix.js) 与 [功能区构造源码](https://raw.githubusercontent.com/soldair/node-qrcode/master/lib/core/qrcode.js)，实施时检查安装版本的对应实现。
- `render.ts`：合成猫图、保护保留模块、绘制静区、组装迎宾卡。
- `verify.ts`：解码与严格比较、有限档位重试、清晰版回退。
- `main.ts`：DOM 事件、页面状态、请求版本检查、下载，保持单一路径。

不预建插件系统、任务队列、通用状态框架或后台管理。

## 4. 绘制与校验约定

1. `qrcode` 根据完整载荷自动生成 H 纠错矩阵；不设置过小的固定版本，不手动固定掩码。
2. 取全部保留模块。定位图案及白色分隔区、时序、对齐、格式/版本信息和固定深色模块按原矩阵完整绘制。
3. 设矩阵边长为 N，单元像素边长为 `ceil(1024 / (N + 8))`，含静区的二维码图边长为 `(N + 8) × 单元像素边长`。每边四模块白底，整数像素落点。
4. 猫图裁剪后只进入矩阵内容区。普通数据模块采用原图纹理配合黑白核心，依次尝试 0.60、0.75、0.90 的核心边长比例；黑白核心不能受原图透明度影响。
5. 每档至少校验原始 PNG 像素和含完整静区的 320px 宽缩小图；解码文本必须与完整载荷一致。UI 只有在完成校验后才提供下载。屏幕实际展示宽度小于 320px 时追加该宽度校验，不能把未检验的更小预览标为通过。
6. 三档都失败时绘制标准模块，将猫图放在二维码静区外，重新解码；仍失败则返回可理解错误，禁止导出。
7. 迎宾卡组合后再对整张图片解码；排版文字不能覆盖静区。最终存储并下载同一 Blob，避免预览和导出来自不同版本。
8. 用户改表单、换图或调整裁剪，递增请求编号并废止旧结果。任何旧解码或旧图片回调不能恢复下载按钮。
9. 手动“增强识别”以当前档位的下一档为起点，只向更清晰档递进；0.90 档之后采用清晰版，清晰版下隐藏按钮。每次都重新验证最终 Blob。

第一阶段可在上述三档范围内调整纹理强度和图像明暗，但不得为了通过而侵入保留区、缩小静区、修改输入或跳过校验。参数调整需更新固定图片回归结果。

## 7. 质量检查矩阵

| 类别 | 必测用例 |
| --- | --- |
| Wi-Fi 正常 | ASCII SSID、中文 SSID、开放网络、隐藏网络、合法 ASCII 密码、64 位十六进制 PSK |
| 字符边界 | 1/32 字节 SSID、超 32 字节、密码 7/8/63/64 位边界、全十六进制名称、前后空格、真实引号、反斜线/分号/逗号/冒号组合 |
| 非法输入 | 空 SSID、密码网络空密码、控制字符、首版不支持的密码字符；保证错误不会降级为开放网络 |
| 图片 | Tom、黑猫、白猫、杂乱背景猫、横图、竖图；透明 PNG；方向信息；损坏、超大及不支持格式 |
| 自动解码 | 六张猫图 × 十种固定合法载荷，全部最终输出解码一致；320px/原始尺寸；交叉解码器；清晰版路径也覆盖 |
| 可扫余量 | 对固定样例做轻度旋转、缩放与 JPEG 重压缩探测；失败回归到对应参数调优，不据此宣称覆盖所有拍摄条件 |
| 状态 | 生成时连续修改、快速换图、重复生成、下载后再修改；旧结果不能覆盖新请求 |
| 导出 | 下载与当前预览一致；文件名无密码；整张 PNG 有静区且能反解；手机保存路径可用 |
| 隐私 | 页面加载后提交/换图/下载无数据请求；检查 URL、存储与日志无输入；拦截第三方网络依赖后功能仍可用 |
| UI | 375/768/1440px；长中文 SSID；键盘焦点、裁剪替代控件、状态朗读、减少动态效果 |
| 真机 | iPhone + Android：默认 Tom、上传照片、增强识别；实际 WPA2 网络与开放网络；特殊字符/中文 SSID；记录相机识别与联网结果各自是否成功 |

持续集成验证不读取真实家庭密码。实体测试记录只写设备、系统、网络类型、用例编号、结果，不提交真实 SSID、密码、家庭照片或真实二维码。

首版只承诺经过测试的网络类型。WPA2/WPA3 混合网络一般走 WPA 兼容路径，但需实机记录；WPA3-only 在 Android 实现中使用 SAE，不能直接写 `WPA3` 期待通用兼容。[Android 实现](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/main/src/com/android/settings/wifi/dpp/WifiDppUtils.java)

1. 完成本地质量检查；核对源码、默认图、测试夹具与输出目录，确认没有真实连接信息。仅构建产物发布到 Pages。

3. Vite `base` 固定 `/hajimiWF/`；所有资源通过构建器或正确基路径引用；无需 SPA 多级路由和自定义 404。GitHub 设置 Pages 来源为 GitHub Actions。[Vite 部署指引](https://vite.dev/guide/static-deploy.html#github-pages)
4. 工作流：检出、Node 24、`npm ci`、类型检查、单元测试、浏览器测试、构建、上传 `dist/`、部署 Pages。Actions 使用经核实的官方版本/提交；不要机械复制过期版本。
5. 权限最小化：`contents: read`、`pages: write`、`id-token: write`；环境 `github-pages`，同一部署并发组；PR 只验证，`main` push 或手动触发才部署。
6. 取得工作流实际返回的部署 URL，打开验证子路径、刷新、默认图、上传、生成、下载和 HTTPS。用一次线上生成结果完成实机连接测试。
7. 记录提交 SHA、工作流链接、部署 URL、测试设备与日期，完成后建立 `v1.0.0` 标签。最终交付提供真实站点与仓库链接，不把推测 URL 当作已上线证据。

预计站点目标为 `https://zsnmfj-tech.github.io/hajimiWF/`，尚未创建或部署，不保证该地址目前可访问。

回退：对引入问题的提交使用普通 revert，恢复上一已验证版本并重跑部署；不改写远端历史。没有数据库或用户持久数据，无迁移工作。首次发布尚无稳定版本时停用错误部署并发布修复版。已下载二维码是静态 Wi-Fi 载荷，回退网站不能撤销它；更换网络密码后需重新生成图片。

GitHub Free 的 Pages 使用公开仓库；官方限制不将 Pages 用作商业 SaaS/交易业务托管。本计划以免费、浏览器本地处理工具为前提，如果“给客户使用”实际指收费 SaaS，开发前重新选择符合用途的静态托管，前端架构无需改变。[Pages 可用范围](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
