# 哈基米 Wi-Fi：功能设计

设计日期：2026-10-23。用户于 2026-10-24 批准实施；实际进展与验证见[验收记录](验收记录.md)。

需求依据：[idea.md](../idea.md)。配套文档：[开发与部署计划](开发与部署计划.md)、[视觉规范](../DESIGN.md)。

## 1. 产品定义与设计假设

给家里的 Wi-Fi 做一张猫咪二维码。主人填写网络信息，使用默认 Tom 或上传自己的猫照片，生成图片；亲友用手机系统相机扫码，经系统确认后加入 Wi-Fi。

明确来自需求的内容：猫咪主题、可上传猫图、未上传时使用《猫和老鼠》的 Tom、网站公开可用、部署到 GitHub 免费网站。

用户于 2026-10-23 明确确认主视觉：“猫照片融入整张二维码，能看出上传的猫”。猫主体可辨认与二维码可扫码共同作为验收条件。

已批准方案采用以下边界：

- 面向家庭主人和来访亲友，首版简体中文、免费使用、无需注册，没有收费交易或商业 SaaS 管理功能。
- 默认图保留 Tom 角色要求。开发阶段用 imagegen 制作清晰、适合方形裁剪的 Tom 插画并存为本地资源，记录来源；不把其他原创猫当作 Tom 交付，不默认抓取影视截图。
- 首版针对常见 WPA/WPA2 个人网络及开放网络。WPA3-only、企业认证网络不在首版兼容承诺内。

最脆弱的假设是“任意猫图都能兼顾可辨认与稳定扫码”。方案用裁剪、逐级强化二维码、自动解码和明确回退应对；不保证每张照片都能保留同等艺术效果。

## 2. 首版范围

| 编号 | 功能 | 首版行为 | 完成标准 |
| --- | --- | --- | --- |
| F01 | 输入 Wi-Fi | 名称、密码、网络类型、折叠的隐藏网络选项 | 字段合法；特殊字符不丢失、不被修改 |
| F02 | 默认 Tom | 首次打开选中默认 Tom，表单为空 | 不上传即可完成生成与下载 |
| F03 | 上传猫图 | JPEG、PNG、WebP，单图；本地读取、更换、恢复默认 | 横图、竖图均能生成；错误上传不破坏上一次可用图片 |
| F04 | 裁剪 | 固定 1:1；拖动位置、缩放 1–3 倍、重置 | 猫脸能放入画面；键盘可调整位置与缩放 |
| F05 | 猫咪融合 | 猫照片覆盖二维码数据区域；完整保留必要识别结构 | 标准测试图片可辨认猫主体且通过解码 |
| F06 | 自动校验 | 从最终像素反解并与原始 Wi-Fi 载荷逐字节比较 | 校验失败的艺术码不能下载 |
| F07 | 增强识别 | 自动加强码点；用户也可点击“增强识别” | 结果明确标识当前效果；不能伪称已经联网成功 |
| F08 | 下载 PNG | 一张白底迎宾卡，含二维码、网络名和扫码说明 | 下载文件再次解码通过，图片中不明文显示密码 |
| F09 | 使用说明 | 如何扫码、数据如何处理、无法连接时如何检查 | 一屏内找到说明，手机可完成全部操作 |

不纳入首版：账号、数据库、云端图片存储、历史记录、链接内分享密码、动态二维码、短链、付费 AI 生成服务、自动抠图、批量制作、图案商城、其他动物、多语言、PWA、SVG/PDF 导出、公众号或微信专用连接流程。

## 3. 使用流程与页面结构

桌面采用左侧编辑、右侧迎宾卡预览；手机采用同页纵向流程。页面只有一个主要任务，不设计营销落地页或多级导航。

1. 打开页面：显示 Tom 原图与“填写 Wi-Fi 后生成”的明确示意状态；不放看似真实但无法连接的假码。
2. 填写 Wi-Fi 名称与密码；网络类型默认为“有密码（WPA/WPA2）”。
3. 可选上传猫照片，拖动、缩放完成方形裁剪；不上传则沿用 Tom。
4. 点击“生成猫咪 Wi-Fi 码”，显示绘制与校验状态。
5. 成功后展示猫咪二维码及“图片校验通过，请用手机试扫”。
6. 点击“下载 PNG”，保存迎宾卡；可展示在另一台设备上，或打印后摆放。
7. 亲友用系统相机或系统 Wi-Fi 扫码入口扫描，按手机提示确认加入网络。

建议固定文案：

- 产品名：哈基米 Wi-Fi。
- 主标题：让猫咪帮你招待朋友。
- 说明：填好 Wi-Fi，做一张可以扫码连接的猫咪图片。
- 本地处理提示：Wi-Fi 信息和猫照片只在当前浏览器处理。
- 下载区提示：这张图包含连接信息，请分享给你愿意提供 Wi-Fi 的人。
- 扫不出来：保持图片完整、提高展示亮度，或试“增强识别”。
- 已识别但连不上：核对网络名、密码和网络类型，确认手机位于 Wi-Fi 覆盖范围内；增强识别不能修复错误密码或路由器兼容性。

网页本身不能替访客静默修改 Wi-Fi 设置。识别二维码、弹出系统确认、成功接入网络是三个不同结果；页面只知道第一项的本地解码结果。[Wi-Fi 格式与扫描行为](https://github.com/zxing/zxing/wiki/Barcode-Contents#wi-fi-network-config-android-ios-11)

## 4. 输入与图片规则

| 字段 | 规则 |
| --- | --- |
| Wi-Fi 名称 SSID | UTF-8 编码后 1–32 字节；支持中文；保留前后空格、大小写与原始字符，不自动 trim 或 Unicode 归一化；拒绝控制字符 |
| 有密码网络 | 首版接收 8–63 个可打印 ASCII 字符，或 64 位十六进制 PSK；密码默认隐藏，可切换可见；不自动裁去空格 |
| 非 ASCII 密码 | 明确提示“此版本暂不支持中文或表情密码”，不声称所有路由器都不支持；首版范围内不接受 |
| 开放网络 | 不输出密码字段；切换时清空内存中的密码，并提示“已切换为无密码网络” |
| 隐藏网络 | 默认关闭；只输出对应标志，不保证所有系统都自动连接 |
| 上传格式 | JPEG、PNG、WebP；拒绝 SVG、GIF、HEIC 和损坏文件；提示 HEIC 用户先转 JPEG/PNG |
| 图片大小 | 文件不超过 5 MiB，解码后不超过 1600 万像素；超限明确提示；处理前后释放废弃图片对象 |
| 图片处理 | 修正照片方向、透明区域铺白、方形裁剪后缩至 1024×1024；裁剪不保留原图元数据 |

SSID 字节数与字符数不同，输入计数以字节展示。密码规则采用首版明确支持的兼容范围，参考 [wpa_supplicant 配置说明](https://android.googlesource.com/platform/external/wpa_supplicant_8/+/refs/heads/main/wpa_supplicant/wpa_supplicant.conf)。

## 5. 二维码载荷与猫图融合

二维码直接编码 Wi-Fi 载荷，不指向本网站、不含短链。标准示例使用虚构信息：`WIFI:T:WPA;S:CatHome;P:demo12345;H:false;;`。开放网络采用 `T:nopass`，省略密码字段。

网络名与密码中的反斜线、分号、逗号、双引号、冒号按 Wi-Fi QR 约定逐字符转义；不额外包裹整段引号。反解结果必须与转义后的完整载荷一致，测试还必须验证字段还原与原输入一致。[ZXing 格式说明](https://github.com/zxing/zxing/wiki/Barcode-Contents#wi-fi-network-config-android-ios-11)

采用固定 H 纠错、自动选择二维码版本，不为视觉效果自行修改编码内容。猫图融合仅调整绘制：定位、分隔、时序、对齐、格式、版本等功能模块保留原始黑白值；四周至少保留四个模块宽的纯白静区。静区内不画猫耳、爪印、文字、边框或阴影。[DENSO 静区说明](https://www.qrcode.com/en/howto/code.html)

数据区域保留猫图，并在模块中心约束亮度。首轮实测后，为改善自家猫的辨识度，首档采用 0.46 边长的明暗核心并保留照片纹理；后续采用 0.60、0.90 的纯黑白核心。这些比例仍需逐张图校验，不能当作可靠性保证。H 纠错也不等于可以任意遮挡 30% 的图片面积。[DENSO 纠错说明](https://www.qrcode.com/en/about/error_correction.html)

每档检查最终导出的像素及按屏幕尺寸缩小后的像素。若艺术档都失败，输出“清晰版”：完整标准黑白二维码，猫图移至静区外的迎宾卡区域；明确显示“这张照片已切换为更易识别的清晰版”。不得悄悄丢弃用户上传的猫。

清晰版是异常回退，不替代主视觉目标。默认 Tom 和标准猫图测试集必须有融合版通过，才能认为“把 Wi-Fi 画成猫”完成；不能仅凭普通二维码能扫就宣布成功。

“增强识别”从当前已通过的档位向下一更清晰档尝试并重新校验，不能重新从最弱档开始。最高艺术档之后进入清晰版；已是清晰版时隐藏该按钮。修改输入并重新生成才重置为自动选档。

## 6. 状态与错误处理

| 状态 | 页面行为 |
| --- | --- |
| 未填写 | 显示 Tom 与操作提示；下载不可用 |
| 输入有误 | 字段旁就地提示并聚焦首个错误；不清空其他有效字段 |
| 绘制/校验中 | 显示当前状态，防重复提交；旧结果不能下载 |
| 校验通过 | 展示结果及下载；提示手机试扫，不显示“已连接 Wi-Fi” |
| 清晰版回退 | 解释已降低融合程度，保留上传猫图与下载能力 |
| 全部校验失败 | 保留输入，提供重试；不生成损坏文件 |
| 用户修改任何输入或猫图 | 旧结果标为“信息已修改，请重新生成”；立即禁用下载 |
| 异步旧任务返回 | 用递增请求编号丢弃过期结果，不能覆盖新表单的结果 |
| 换图失败 | 保留旧图，显示具体格式、大小或损坏原因 |
| 移动端未直接下载 | 提供当前 PNG 的大图查看入口和保存说明；不申请相册访问权限 |

## 7. 输出与隐私

- 文件名固定为 `hajimi-wifi.png`，不含 SSID 或密码。
- 一张迎宾卡包含猫咪二维码、SSID、“扫码连接 Wi-Fi”；长 SSID 自动换行，不能侵入二维码静区。
- 二维码单元按整数像素绘制，外边距至少四模块；最终卡片按矩阵大小选择尺寸，二维码主体导出不低于约 1024 像素。具体公式见开发计划。
- 不明文打印密码。二维码本身可还原连接信息，图片不是加密凭证。
- SSID、密码、用户照片和输出只保存在页面内存；不写 URL、localStorage、IndexedDB、日志、分析服务、错误上报或远程接口。
- 默认图、字体策略和脚本随站点发布，不引用运行时第三方 CDN；用户照片绝不提交到图片生成服务。仅默认 Tom 资产在开发时制作。
- 不承诺“完全没有服务器访问日志”：GitHub Pages 会记录网站访问所需的部分信息；本应用不主动发送表单或图片内容。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 8. 验收与首版成功定义

| 维度 | 验收标准 |
| --- | --- |
| 主流程 | 默认 Tom、上传猫两条路径都能输入、裁剪、生成、下载 |
| 视觉 | Tom 及五张固定猫图在默认测试载荷下均有融合档通过；在 320px 展示宽度可辨猫主体；不能靠清晰版冒充通过 |
| 内容 | 中文 SSID、特殊字符、首尾空格、64 位 PSK、开放网络、隐藏网络载荷反解一致 |
| 自动解码 | 测试矩阵最终结果全部反解成功；失败艺术码被挡住；下载整卡也需能定位并解码 |
| 真机 | 至少一部 iPhone 和一部 Android，记录型号与系统；系统相机/系统扫码可识别，确认后接入实际 WPA2 网络 |
| 实物 | 在另一屏幕约 50% 亮度下展示，以及二维码主体至少 6cm 的打印件上试扫；每种设备/介质重复三次，均应在正常对焦后约 3 秒内识别 |
| 网页 | 375px 手机及 1440px 桌面无横向溢出；键盘可完成字段、裁剪、生成、下载；结果变化有可访问提示 |
| 隐私 | 生成、裁剪、下载时网络请求中没有表单、图片或二维码载荷；刷新后不由应用恢复数据 |
| 发布 | Pages 子路径下资源、刷新、默认猫、上传、生成、下载均工作；线上验证后才标记已上线 |

真机及打印测试需要实体设备，由项目负责人或协作测试者执行并记录；浏览器模拟和自动解码不能代替。艺术效果若无法通过，先调整绘制参数或经用户同意修改效果目标，再进入正式上线。

## 9. 参考与选择理由

- [qrsticks](https://qrsticks.greg.technology/)：借鉴“输入、画出、下载”的短流程和作品优先。2026-10-23 读取页面发现其绘制请求访问 `/api/doodle` 且将输入写入 URL；本项目不复用这条数据路径。
- [QiFi](https://qifi.org/)：参考 Wi-Fi 表单与本地生成的简单模型；本项目不保存历史网络信息。
- [QR Code Styling](https://github.com/kozakdenys/qr-code-styling)：中心 Logo 是更省时的最小方案，但不能充分表现整张上传猫图，不符合已确认的主视觉目标，因此不采用该路线。
- [Awesome-qr.js](https://github.com/SumiMakito/Awesome-qr.js)：已有背景图融合能力；本方案采用小型 Canvas 绘制层，以精确控制全部保留模块、最终像素与回退，不重写 QR 编码算法。
